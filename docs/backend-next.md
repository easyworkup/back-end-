## Как уменьшить конфликты

- Один исполнитель на доменный модуль до merge текущего PR. KAN-68/69/70/71 не выполняются одновременно в resume.service/controller. Новые профиль/catalog модули отдельны от roadmap controller.
- Prisma schema/migrations, AppModule, contracts, package/lockfile, CI и общие guards принадлежат интегратору. Исполнитель описывает нужное подключение в PR; интегратор делает короткий отдельный change после проверки. Seed каталога отделён от base seed.
- Ветвиться от свежего dev: `feature/KAN-75-catalog-api`. Один PR — одна подзадача. Перед началом отметить в Jira область файлов и исполнителя. Сначала закончить review открытого PR в области, потом начинать следующий.
- PR только в dev, одно одобрение и зелёный CI. Main получает только PR из dev. Мержат участники команды с правом merge. Не переписывать общие файлы ради форматирования, не коммитить generated/deps/.env.
- Перед PR обновить свою ветку из dev, решить конфликты локально, повторить проверки своей области. SQL миграцию добавлять после последней уже принятой миграции, старую не редактировать.

## Минимум для сдачи джуном

В PR написать: URL/операция, входной fixture, ожидаемый ответ, затронутые файлы, команды проверки. Показать happy path и минимум одну существенную ошибку: чужой userId, пустое поле, конфликт revision или повтор запроса. Тестировать свой сервис/HTTP, а не только то, что mock вернул mock. Попросить наставника проверить владение данными до объединения.

Начать с `docs/api-contract.md`, `docs/database.md`, DTO своей операции и существующих tests. Общие правила и детализация задач: [KAN-48](https://work-up.atlassian.net/browse/KAN-48).
